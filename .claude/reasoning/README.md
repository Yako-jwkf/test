# 推論の状態ファイル

要約: 会話をまたいで持つ推論の状態(本題・指摘・命題)を `state.md` に書き出す。返答の前に読み、返答の後に更新する。頭の中だけで持つと、ターンごとに本題を落とし、報告を事実に格上げするため(2026-10-01 の事例2)。

## いつ使うか
- 評価・設計・調査を頼まれたターンと、指摘を受けたターン。単純な質問や1回で終わる作業では使わない。
- 新しい会話の最初のターンでは作り直す。前の会話の状態は引き継がない。
- `state.md` はコミットしない(`.gitignore` 済み)。

## 手順
1. 返答を書く前に `state.md` を読む。なければ下の書式で作る。
2. **本題**: 今回の発言が、本題のどの部分の続きかを書く。本題そのものは、貼られた文の表面(例: テストの話)ではなく、会話全体で何をしたいのかから決める。変わったと判断したら、理由を添えて書き換える。
   - **評価の軸**(評価を頼まれたターンだけ): 評価する文書が自分で書いている目的・原則・意図の宣言(例:「表示＝演出」「分離する」「最重要原則」)を、原文のまま「評価の軸」の表に全部並べる。節ごとに目的が違えば節ごとに拾う。会話全体の目的も1行入れる。各行の「この意図で開く分岐」に、その意図があるから**その先にできること**(と、閉じること)を書く。今の得と損(コスト・正確さ)だけで評価しない。例: 表示を時刻から切り離した演出のカウンタは、推定した状態で進みを変える・時刻に見えない数で時計を気にさせる心配をなくす、などを開く。現在時刻 − 開始時刻を出すだけのカウンタには、その先がない。各行の「対応」には、その分岐まで見て評価した命題の番号か「対象外(理由)」を書く。評価の対象は一文で言い直すが、軸は1本に絞らない。分岐か対応が空の行があれば `state-guard.py` が止める(2026-10-02、メモが自分で書いた「表示＝演出」を軸にせず、パフォーマンスと進行感の観点を落とした。続けて「得を先に書く」と直そうとしたが、利用者の基準は「そこからの分岐を考慮してほしい」だった)。
3. **指摘**: ユーザーの言葉のうち、指摘・呼び名・皮肉・繰り返し出てくる言葉を、原文のまま足す。私のどのミスに当たるかと、対応したかを書く。ミスに当たるもの(自分で気づいたミス、テストや安全チェックで分かったミスも)は、その場で `docs/knowledge/mistake-inbox.md` にも1行足す。`state.md` はコミットしないので、ここにしか書かないと消える。書き漏れは `.claude/hooks/inbox-guard.py` が返答の終わりで止める。指摘でなかったときは、返答に「指摘ではない」と理由を書く。
4. **命題**: 返答で使う主張を足す。種類(下の表)と、依存している命題を書く。導出の依存には、置いた仮定(例:「このセッションのサブエージェントを使う」)まで全部書く。書かない仮定があると、結論が実際より強く見える。
   - 相手の設計の部品を「不要」「欠点」とする命題は、依存にその部品の目的(原文の引用か、ユーザーへの確認)を書く。目的が分からなければ判断せず、聞く。
   - 性能・手間・費用の比較(「同じ」「軽い」「重い」)は、測ったなら「外部確認」、測っていないなら「推測」にする。「導出」にしない。
5. 返答を書く。1行目は「本題: ○○。今回はその△の部分」。本題の欄を書き換えたときは、返答に「本題の変更」として前後を書き、ユーザーに確認を求める。(`.claude/hooks/state-guard.py` が、更新漏れと無断の書き換えを止める)
6. 返答を出す前に、次を点検する。
   - 「報告」の命題だけを根拠に、相手の主張を肯定・否定していないか。
   - 「確かめた」と書いたのは、種類が「外部確認」の命題だけか。
   - 「指摘」に、対応していないものが残っていないか。
   - 評価のターンなら、「評価の軸」の各行に、開く分岐と、命題の番号か「対象外(理由)」があるか。
   - 「しかない」「できない」「必ず」と書いた結論は、依存に仮定が残っていないか。残っていれば、仮定を書いて弱める。
   - 選択肢の「気になる点」(推測)のうち、数分で確かめられるものを確かめずに残していないか。確かめられるなら確かめてから載せる。確かめないなら「未確認。確かめ方: ○○」と書く。
7. 指摘で崩れた命題は、状態を「撤回」にする。それに依存している命題も見直し、状態を「撤回」か「有効(見直し済み: 理由)」にする。見直し漏れは `state-guard.py` が止める(依存の欄に命題の番号を書いておかないと、つながりを追えない)。

## 命題の種類

| 種類 | 意味 | 返答での書き方 |
|---|---|---|
| 外部確認 | 実行結果・テスト・ユーザーへの確認など、文章の外から返ってきたもの | 「確かめた」と書いてよい |
| 報告 | 論文・記事・ドキュメントに書いてあること | 「○年の△では〜と報告(本文/要約のみ)」。決め手にしない |
| 導出 | 筋道で出したもの | 依存している命題を示す |
| 仮定 | 置いた前提 | 「〜と仮定すると」 |
| 推測 | 確かめていない見込み | 「〜と推測する」 |
| 私の意見 | 自分の考え | 「私の意見」と書く |

検索で見つけたものは「報告」で、「外部確認」ではない。検索結果も文章でしかない。

## 書式

```
# 推論の状態(会話: YYYY-MM-DD 〜「最初の依頼の要約」)

## 本題
- 会話全体の目的:
- 今回の発言の位置づけ:
- 本題の変更履歴:

## 指摘
| ターン | 原文 | 当たるミス | 対応 |
|---|---|---|---|

## 評価の軸(評価を頼まれたターンだけ)
| 軸(原文) | 出どころ(文書の節/会話の目的) | この意図で開く分岐 | 対応(命題の番号 / 対象外(理由)) |
|---|---|---|---|

## 命題
| id | 命題 | 種類 | 依存 | 出どころ(年・本文/要約) | 状態 |
|---|---|---|---|---|---|
```
