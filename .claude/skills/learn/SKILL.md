状態の書き方: `docs/knowledge/provenance-format.md`(本人・本人確認・確かめた・資料・AI の解釈・委任・不明)。

## 守ること
- 上位の概念と前提の概念を同じものとして扱わない。[C1]
- 学ぶ順を勝手に確定しない。順の案を出したら、ユーザーの確認を待つ。[C2] [T10]
- 入口を上位の概念からに限らない。どこから入ってもよい。[C3]
- 決まっていない関係の分類や学ぶ順の基準を、ユーザーの意図として扱わない。[C4] [U1] [U2]
- 現在地があいまいなら、確定せずに聞く。[C5]
- ユーザーが指定していない既存のフレームワークや固定の分類を持ち込まない。[relations.constraint]
- 復習の予定(間隔反復のスケジュール)は組まない。[scope.excluded](この「対象外」には出どころが書いていない。ユーザーが外したものか未確認)
- 基本の出力(現在地・上位・前提・関連・下位・学ぶ順・Recall)を、毎回同じ深さで機械的に埋めなくてよい。[deliverable]
- AI が出した概念や説明は「AI の解釈」として出す。「確かめた」と書かない。教科書などから取ったときは「資料」と書き、本文を読んだか要約だけかも書く。(要件外。`provenance-format.md`)
- 専門用語には短い説明を添える。(CLAUDE.md)

## 手順
一度に全部を出さない。1 → 2 → 3(確認を待つ)→ 4(答えを待つ)→ 5 → 6 と、ユーザーの返事を待ちながら進める。

1. **現在地を決める** [T1] [concept_structure.current]
   - 入力をそのまま現在地の候補にする。入口は、分野・具体的な概念・概念どうしの関係・すでに知っている概念の Recall のどれでもよい。[target]
   - 一意に決まらないとき(同じ名前で別の概念がある、範囲が広すぎるなど)は、候補を並べて「どれのことか、番号で教えてください」と聞く。[C5]
   - 「もう知っている」「覚えているか試したい」と言われたら、先に手順4の Recall から始める。[target: 既知概念のRecall]
2. **地図を出す** [T2〜T6]
   - 上位: 現在地を理解するのに必要な範囲を基本にし、必要なら広い分野まで広げる。[upper] [T2] [T3]
   - 前提: 現在地を理解するために先に要る概念。上位とは別に書く。[prerequisite] [C1] [T4]
   - 関連 [T5]、下位 [T6]。
   - 関係は基本の4つ(上位・前提・関連・下位)を使う。必要なら詳しくしたり、関係の種類を足したりしてよい。足したときは「足した関係」と書く。[relations.rule]
   - 分野から入ったときは全体から詳細へ、細かい概念から入ったときは全体の中での位置も示す。[core_principle.learning_directions]
   - 形は表にする。

     | 関係 | 概念 | 一言の説明 | 状態 |
     |---|---|---|---|
     | 現在地 | (入力) | | 本人 |
     | 上位 | | | AI の解釈 |
     | 前提 | | | AI の解釈 |

3. **学ぶ順の案を出して、確認を待つ** [T7] [T10] [learning_order]
   - 学ぶ順の基準は決まっていない。[U2] 案を出すときは、その順にした理由を1行ずつ書き、「AI の解釈」として出す。
   - 「この順でよいか、変えたいところがあれば教えてください」と聞き、返事があるまで確定しない。確認されたら「本人確認」にする。
4. **Recall** [T8] [recall.flow]
   - 何も見ずに答える問いを出す。答えは先に見せない。
   - ユーザーの答えを受けて、概念ごとに「答えられた・不足・誤り・あいまい」に分けて示す。その結果は「確かめた」になる。
5. **戻る先を決める** [T9] [U3]
   - 戻る先を選ぶ基準は決まっていない。[U3] 不足・誤り・あいまいが出たら、戻る先の候補を絞らずに並べ、「番号で教えてください」と聞く。候補は次の2つの軸で出す。
     - **どの概念へ**: 前提・上位・関連の、どの概念に戻るか。[T9]
     - **どの段階へ**: 理解し直す/覚え方を変える/思い出す練習を増やす/時間を空けてもう一度/使ってみる。(要件外。出どころ: 別の AI との会話でまとめた「学習・記憶システムの全体像」45節の学習のデバッグ。v0.3 には入っていない、AI の解釈)
6. **終わり方** [U4] [U5]
   - したこと(現在地・確認した学ぶ順・Recall の結果・戻った先)を短くまとめる。
   - 理解状態の更新のしかた(点数のつけ方など)は決まっていない。[U4] Recall の結果は「答えられた・不足・誤り・あいまい」のまま書き、点数や段階に変えない。
   - 理解状態をファイルに残すかどうかは決まっていない。[U5] 最後に「この地図と Recall の結果をファイルに残しますか」と聞く。残すと言われたら置き場所も聞く(案: `docs/learning/notes/<概念>.md`)。書くときは、各行に状態と出どころを付ける。

## Story / Rhyme(物語・語呂) [D1]
v0.3 では「Agent に委任」とだけあり、委任先と範囲は書いていない。このスキルでは、次のときだけ案を出す(AI の解釈。出どころ: 「学習・記憶システムの全体像」19節・21節)。
- ユーザーが頼んだとき。
- 年号・順番・数値のような事実で、作る手間より覚えやすさの得が大きそうなとき。
- もともと因果関係があるものは、物語にせず、実際の因果を説明する。

## 成功の基準
v0.3 には成功の基準(success_criteria)がない。今は試しに使い、良し悪しはユーザーが決める。使って気づいたこと(決めたい U1〜U5、足したい手順)は、要件の改訂案として要件定義 Agent に渡す。

## 注意
- 学習の流れの中の問いは「番号で教えてください」「この順でよいか教えてください」の形にする(学習の中の選択は、作業の進め方を決める選択とは別のため)。PR #8 では、選択を求める返答に「候補」の節を求める点検(`state-guard.py`)と一緒に作ったが、その点検は main に入れていない(2026-10-06、[pending-mechanisms.md](../../../docs/knowledge/pending-mechanisms.md))。入れるときは、この形の問いが点検に当たらないことを確かめる。
