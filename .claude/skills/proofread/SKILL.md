対象: 技術文書(手順書、仕様の説明、API の説明など)。

## 目的

文章を特定の文体へ変換するのではなく、読者が文章内の対象・主体・作用・条件・結果を正しく追跡できる状態にする。

最優先は「原文の情報を保存すること」。その上で、意味が一意に取れない箇所だけを最小限直す。問題のない文章は一文字も変えない。

## 出力の形

次の3つを必ずこの順で出す。

1. **修正後の全文**。変更が1つもなければ原文をそのまま出し、「変更なし」と書く。
2. **変更一覧**。1件ずつ「場所 / 問題の種類 / 修正前 / 修正後 / 根拠(原文のどこから分かったか)」。根拠に原文の引用を書けない変更は、取り消して「確認したい点」へ移す。
3. **確認したい点**。原文だけでは決められなかった箇所。本文は原文のままにし、「何が決められないか」と選択肢を書く。直した箇所でも、別の読み方が残るならここに書く。

## 直すか、確認に回すかの決め方

- 読者が一意に特定できない箇所があるか(指示語の参照先、主体、作用対象、条件の係り先、因果の種類)。なければ変更しない。
- その答えが原文の他の箇所から最も自然に読めるなら、直して、変更一覧に根拠を書く。
- 原文に手がかりがないなら、本文は変えず「確認したい点」に書く。推測で埋めない。

## 1. 参照対象を確認する

「これ」「それ」「こちら」「前者」「後者」などの指示語を機械的に禁止しない。
確認するのは、指示語の参照先を読者が一意に特定できるか、だけ。

悪い例: AとBを設定した後、それを削除します。
「それ」がAなのかBなのか、両方なのか不明。
原文に手がかりがないので本文はそのまま。確認したい点: 「『それ』は A、B、両方のどれですか。」

一方、「AとBを設定した後、それを削除します。Bは一時的な設定だからです。」なら、理由の文から「それ」= B と読めるので「Bを削除します」に直し、根拠に「Bは一時的な設定だからです」を書く。

## 2. 主体を確認する

「誰が何をするのか」が必要な箇所だけ明示する。

悪い例: エラー発生時は再試行し、失敗した場合はログに残します。
誰が再試行し、誰がログを記録するのか不明。
修正: エラーが発生した場合、クライアントはリクエストを再試行します。再試行に失敗した場合は、クライアントがエラー内容をログに記録します。
ただし、主体が原文から分からないなら勝手に作らない。

## 3. 作用対象を確認する

動詞だけでなく、何が何に作用しているのかを見る。

悪い例: 設定を変更すると、これを防ぐことができます。
修正: タイムアウト時間を変更すると、リクエストの長時間待機を防げます。
ただし、「これ」が何なのか原文から分からないなら、勝手に具体化せず、本文はそのままにして「確認したい点」に書く。

## 4. 条件の係り先を確認する

「いつ」「どの場合」「どこまで」が何にかかっているのかを確認する。
例: 管理者としてログインした場合のみ、APIを利用できます。([管理者としてログイン] →条件→ [APIを利用できる])
条件が複数ある場合も、それぞれの係り先を明確にする。

## 5. 因果関係を確認する

「AだからB」なのか、「AするとB」なのか、「Aの場合にBが起きる」なのかを区別する。
曖昧: キャッシュを入れるとパフォーマンスが改善します。
「パフォーマンス」が何を意味するのか不明なら、周辺情報から特定できる場合だけ対象を明確にする。
キャッシュを導入すると、DBへのアクセス回数を減らせます。
ただし、「レスポンス時間が短くなる」と書いていないなら、勝手にそう変換しない。

## 6. 抽象度を勝手に変えない

具体的に書けば必ず良くなるわけではない。
原文: データを保存する前に確認してください。
やってはいけない変換: データベースに保存する前に、スキーマと必須項目を検証してください。
これは原文にない情報を追加している。「DBなのか」「何を確認するのか」すら原文にはない。
したがって、情報不足ならそのままにして「確認したい点」に書く。「内容を」のような語も原文にはないので足さない。

## 7. 比喩は機械的に排除しない

「壊れる」「詰まる」「流れる」「潰す」「食う」などを全部禁止しない。
見るべきなのは、その比喩が技術的意味の誤解を生むか。
原文: この処理はメモリを食うので、大量のデータを一気に渡すと落ちます。
自然な文脈なら、そのままでも意味は通る。
必要なら、「この処理はメモリを多く使用するため、大量のデータを一度に渡すと落ちます。」程度にする。「落ちます」を「落ちることがあります」にはしない(確実さを変えない)。
「OOMでプロセスが終了する」などの具体的な仕様は、原文や別の確認済み情報に存在する場合だけ追加する。

## 8. 非生物主語を機械的に排除しない

「APIが401を返します。」「キャッシュがDBアクセスを減らします。」「Redisはキャッシュとして使用できます。」
こうした表現は技術文書として普通に成立する。非生物主語だから人間を主語にする、とはしない。見るのは意味関係が明確かどうか。

## 9. 定型句は「AIっぽいから」ではなく情報価値で判断する

「ここで重要なのは〜」「もちろん〜というわけではありません。」「ぜひ参考にしてみてください。」「いかがでしたでしょうか。」など。
これらはAI文章で頻出することがあるが、単純な禁止語リストにはしない。その文が情報を追加しているか確認する。情報を追加していなくても本文からは消さず、「確認したい点」に削除候補として書く。

## 10. 箇条書き・太字・装飾を抑制する

箇条書き=AI ではない。列挙する情報なら箇条書きのほうが読みやすい。
逆に、短い説明を大量の箇条書きに分解して情報の関係を壊しているなら、地の文へ戻す。形式ではなく情報構造を見る。

## 11. 文の長さを固定しない

「30〜45文字」のような固定ルールは採用しない。見るべきなのは、一文に命題が詰まりすぎていないか、修飾関係を追えるか、主節と従属節を区別できるか、文を分割すると理解しやすくなるか。結果として短くなる場合も長くなる場合もある。

## 12. 最重要:最小修正

問題がある箇所だけ直す。
「Redisはインメモリデータストアです。」「APIが401を返します。」「キャッシュを使うとDBへのアクセスを減らせます。」なら、そのまま。
「もっと人間らしくしよう」として改変しない。

## 13. 情報保存を最優先する

修正前後で最低限、以下を比較する。

| 項目 | 保持するもの |
|---|---|
| 主張 | 何を言っているか |
| 数値 | 数値・単位 |
| 条件 | 適用条件・例外 |
| 因果 | 原因と結果 |
| 不確実性 | 「可能性がある」等 |
| 対象 | 何について話しているか |
| 主体 | 誰・何が行うか |
| 抽象度 | 勝手に具体化・一般化しない |
| 技術仕様 | 原文にない仕様を追加しない |

特に、読みやすくするために新しい情報を足さない。

## 14. 編集後の検証

修正前 → 意味構造を抽出 → 問題箇所を特定 → 最小修正 → 意味構造を再抽出 → 差分確認。

変更一覧の各行に原文からの根拠を書けない変更は取り消す。

チェック: 主体は変わっていないか / 対象は変わっていないか / 指示語の参照先は変わっていないか / 因果関係は変わっていないか / 条件を落としていないか / 不確実なものを確定事項にしていないか / 原文にない情報を追加していないか / 抽象度を勝手に変更していないか

## 思想

「AIっぽい文章に変なところがあるから人間っぽく書き直す」のではなく、「文章内の参照・主体・対象・条件・作用関係を検査し、意味が正しく伝わらない箇所だけ最小限修正する」。
「こう変換する」ではなく「問題があるか判定してから変換する」。

入力 → 意味構造の確認 → 問題なし→原文維持 / 問題あり→問題の種類を特定(参照対象が曖昧・主体が不明・作用対象が不明・条件の係り先が不明・因果関係が曖昧・冗長・重複・不要なメタ情報)→ 最小限の修正 → 原文にない情報が追加されていないか検証 → 出力
