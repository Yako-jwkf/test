要件定義の入口。手順の中身は、利用者が要件定義 Agent と作った `prompts/requirement-agent-v1.4.md` に従う(ここに写さない)。
作った理由: 2026-10-11、継続学習機構の会話で、要件を確かめずに設計・実験・部品づくりに進み、「頭悪すぎるので要件定義から始めてください」「要件定義スキルも使わずに仕事をしないAIは必要ありません」と言われた(ミス置き場の 2026-10-11・10-12 の行)。

## 手順
1. `prompts/requirement-agent-v1.4.md` を全部読む。
2. 同じ主題の下書きが `docs/requirements/` にあれば読み、続きの版にする。なければ `docs/requirements/<主題>-v0.1.yaml` を作る。前の版は消さない。
3. 依頼の原文から抽出する(v1.4 の 9節の順)。各項目に state と source_span を付ける。利用者が貼った別の AI の文は、利用者が「これを採る」と言うまで要件にしない。input_coverage に、何を採らなかったかと理由を書く。
4. 決まっていないことを質問にする(v1.4 の 13節: 1回に3つまで。成果物→範囲→成功の条件の順。「未定」「分からない」「任せる」「自由に書く」を必ず許す。選択肢で誘導しない)。
5. 利用者に見せる文の書き方(2026-10-12、記号だらけの質問に「なんの話をしているのですか？」と言われた):
   - 最初の1〜2文で、いま何をしていて、なぜ聞くのかを書く。
   - 項目の記号(D3・S1 など)と状態の英語(BLOCKED・READY など)は、YAML の中だけで使い、利用者に見せる文には出さない。
   - 質問ごとに、答えで何が変わるかを1文で書く。
6. 利用者が「任せる」「全権限」などで判断を渡したら、v1.4 の 7節どおり delegated と記録し、decision_bounds に利用者の原文を書く。そのうえで決め、決めた値と理由を1行ずつ残す。決めた値を user_stated・user_confirmed にしない。
7. sufficiency が READY になるまで、設計・実験・実装に進まない。READY でも、依頼に「実装を開始しない」などの制約があれば守る。
8. 版を上げたら change_history に1行足す。YAML の置き場所と版を、返答の最後に1行で伝える。
