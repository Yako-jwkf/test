## 何を測るか

「ルールがあると良い答えになり、ないと悪い答えになる」ことを確かめます。片方だけでは足りません。ルールなしでも通る事例は、その行を削れる根拠になります(「してはいけないこと」は10行まで、の運用に使う)。

答えは毎回変わるので、同じ事例を複数回流します。

## 引数

- 事例番号(例: `1`、`1,3`)。省略すると全事例。
- 回数(例: `回数=5`)。省略すると3回。

## 手順

1. `docs/knowledge/mistake-cases.md` を読み、対象の事例から「入力(ターン1〜)」と「良い答えの条件」を取り出す。入力が原文でない事例(「原文待ち」と書かれているもの)は流さず、最後に「未実施」として報告する。要約を流しても元のミスは再現しないため。
2. 事例ごとに、`subject`(CLAUDE.md あり)と `subject-bare`(CLAUDE.md なし)を、それぞれ回数ぶん起動する。独立した起動なので同じターンでまとめて出してよい。渡す依頼文は次の形にする。条件や「悪い答え」は渡さない。渡すと答えが条件に寄ってしまい、ルールの効果が測れなくなる。

   ```
   <入力(ターン1)の原文をそのまま>
   ```

3. 入力が2ターン以上ある事例は、1ターン目の答えを受け取ってから、同じサブエージェントに2ターン目の原文を送る(SendMessage で続きを送る)。別のサブエージェントを新しく起動すると、指摘を受けた後の挙動が測れない。
4. 返ってきた答えごとに `judge` を起動し、次の形で渡す。

   ```
   ## 答え
   <答えの全文>

   ## 良い答えの条件
   1. <条件1>
   2. <条件2>
   ...
   ```

   2ターンの事例では、ターンごとに答えを分けて渡し、条件にはどのターンを見るかを添える。
5. 結果を次の表にまとめる。セルは「合格した回数 / 流した回数」。該当なしは分母から外し、注記する。

   | 事例 | 条件 | ルールあり | ルールなし | 判定 |
   |---|---|---|---|---|
   | 1 | 1 | 3/3 | 0/3 | 効いている |
   | 1 | 2 | 3/3 | 3/3 | ルールなしでも通る(削除候補) |
   | 1 | 3 | 1/3 | 0/3 | 書き方を直す |

   判定の決め方:
   - あり が過半数で合格、なし が過半数で不合格 → **効いている**
   - あり も なし も過半数で合格 → **ルールなしでも通る(削除候補)**
   - あり が過半数で不合格 → **書き方を直す**
   - それ以外(割れている) → **判定保留。回数を増やす**

6. `docs/knowledge/retest-log.md` に、日付・CLAUDE.md のコミット番号(`git log -1 --format=%h -- CLAUDE.md`)・表・判定を追記する。履歴が残ると「この行は何回続けて効いていないか」が言えるようになる。
7. 「書き方を直す」「削除候補」になった行について、書き換え案を出す。CLAUDE.md と mistake-cases.md は書き換えない。直すかどうかは利用者が決める(/reflect と同じ線引き)。

## 報告の形

1. 結果の表
2. 判定ごとの一言(なぜそう読めるか)
3. 書き換え案(あれば)
4. 未実施の事例と理由
5. 限界: 回数が少ないこと、judge も AI であること、「ルールなし」は全ルールを外した条件であること

## してはいけないこと

- subject に条件や悪い答えを渡さない。
- 事例の入力を言い換えない。原文のまま流す。
- CLAUDE.md、mistake-cases.md を書き換えない。
- 判定が割れたまま「効いている」と書かない。
