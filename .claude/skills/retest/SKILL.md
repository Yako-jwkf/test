name: retest
description: CLAUDE.md の「してはいけないこと」や、それが指す仕組み(.claude/reasoning/ など)が実際に効いているかを、docs/knowledge/mistake-cases.md の事例を条件ごとの専用フォルダで `claude -p` に答えさせて確かめる。ルールを追加・変更・削除した直後(/reflect で追記した後)、「ルールを再テストして」「効いてるか確かめて」「この行は消していいか」と言われたとき、ルールを減らしてよいか迷うときに使う。CLAUDE.md の文章を採点するのではなく、ルールの有無で答えが変わるかを測る。
---

## 何を測るか

「仕組み(CLAUDE.md と、それが指す手順やファイル)があると良い答えになり、ないと悪い答えになる」ことを確かめます。条件は3つです。

| 条件 | 中身 | 比べて分かること |
|---|---|---|
| `mech` | 今の作業中の版(未コミットの変更を含む) | `mech` と `prev` の差 = 新しい仕組みの効果 |
| `prev` | 仕組みを入れる前の版(`run.py` の `PREV_REF`。既定は 12f8bd7) | `prev` と `none` の差 = 前からあった CLAUDE.md の効果 |
| `none` | CLAUDE.md なし | 基準 |

答えは毎回変わるので、同じ事例を複数回流します。ルールなしでも通る事例は、その行を削れる根拠になります(「してはいけないこと」は10行まで、の運用に使う)。

## 答える役の動かし方(2026-10-01 に作り直し)

答える役はサブエージェントではなく、`claude -p` を条件ごとの専用フォルダで動かします(`run.py`)。理由:

- サブエージェントには親セッションの CLAUDE.md が読み込まれ、版を切り替えられない(worktree でも同じ)。
- サブエージェントは CLAUDE.md の「ナレッジを読む」に従って `mistake-cases.md` を開き、採点条件を読んでしまった(2026-10-01)。
- `claude -p` は、動かしたフォルダの CLAUDE.md を本番どおり自動で読み込む。

`run.py` がすること:
- 回ごとに専用フォルダ(`/tmp/retest-sandboxes/`)を作り、条件の版のファイルを置く。答え合わせになるファイル(`run.py` の `LEAK_FILES`)は置かない。
- フォルダの設定で、本体のリポジトリと出力先の読み書き、Bash を止める。`bypassPermissions` でも deny は効く。`acceptEdits` では `.claude/` の下に書けず、状態ファイルを試せない。
- 会話番号を毎回新しく指定する。指定しないと親セッションと同じ番号で動く。
- モデルは `claude-opus-5-5`(環境変数 `RETEST_MODEL` で変更可)。指定しないと別のモデルで動いた。
- 2ターン目以降は `--resume` で同じ会話に送る。

## 引数

- 事例番号(例: `2`)。
- 回数(例: `回数=5`)。省略すると3回。
- 条件(例: `mech,none`)。省略すると3つとも。

## 手順

1. `docs/knowledge/mistake-cases.md` の対象事例に、入力の原文があるか確かめる(「原文待ち」は流さず、未実施として報告)。
2. **計画を書いて見せる**: `<出力フォルダ>/plan.md` に次の4行を書く(書かないと `run.py` が動かない)。
   - `測りたいもの:` 今回の変更のうち、何の効き目を知りたいか
   - `使う条件:` それを実際に測る「良い答えの条件」の番号。測る条件がなければ、流さずに事例づくりに戻る
   - `費用の見込み:` 回数×ターン数×1ターンの費用。利用者のアカウントの利用枠を使い、上限に達すると途中で止まることも書く
   - `結果で決めること:` どういう結果なら何をするか(進める/直す/やめる)
   計画と費用の見込みを利用者に見せ、了承を得てから流す。
3. `python3 .claude/skills/retest/run.py <事例> <回数> <出力フォルダ> [条件]` を、Bash の run_in_background で直接動かし、終了の通知を待つ。終わりを待つ処理を自分で作らない(2026-10-02、待つ処理が自分自身に一致して終わらなかった)。出力フォルダは scratchpad の下にする。1ターンあたり数十秒〜数分、費用は 2026-10-01 の試験で1ターン 0.1〜0.4 ドル。
4. 終わったら、各回の `answers.md` ごとに `judge` を**2体**起動し、次の形で渡す。条件にはどのターンを見るかを添える。どの条件の答えかは伏せる(ファイル名を番号にする)。2体の判定が割れた条件だけ、3体目に採点させて多数決をとる(2026-10-02、同じ形の答えで合否が割れたため)。

   ```
   ## 答え
   <answers.md の全文>

   ## 良い答えの条件
   1. <条件1>
   ...
   ```

5. 結果を次の表にまとめる。セルは「合格した回数 / 流した回数」。該当なしは分母から外し、注記する。

   | 事例 | 条件 | mech | prev | none | 判定 |
   |---|---|---|---|---|---|

   判定の決め方(過半数で合格かどうかで見る):
   - mech 合格・prev 不合格 → **新しい仕組みが効いている**
   - prev 合格・none 不合格 → **前からの CLAUDE.md が効いている**(mech も合格なら維持できている)
   - 3つとも合格 → **仕組みなしでも通る(削除候補)**
   - mech が不合格 → **書き方を直す**。2回続いたらルールではなく仕組み(フック)を検討
   - 割れている → **判定保留。回数を増やす**

6. `docs/knowledge/retest-log.md` に、日付・CLAUDE.md のコミット番号(`git log -1 --format=%h -- CLAUDE.md`、未コミットの変更があればそう書く)・表・判定を追記する。
7. 「書き方を直す」「削除候補」になった行について、書き換え案を出す。CLAUDE.md と mistake-cases.md は書き換えない。直すかどうかは利用者が決める。

## 報告の形

1. 結果の表
2. 判定ごとの一言(なぜそう読めるか)
3. 書き換え案(あれば)
4. 未実施の事例と理由
5. 限界: 回数が少ないこと、judge も AI であること、専用フォルダには答え合わせになるファイルを置いていないこと(本番より情報が少ない)、Bash を止めていること

## してはいけないこと

- 答える役に条件や悪い答えを渡さない。答え合わせになるファイルを専用フォルダに置かない。
- 事例の入力を言い換えない。原文のまま流す。
- CLAUDE.md、mistake-cases.md を書き換えない。
- 判定が割れたまま「効いている」と書かない。
- 会話番号を指定せずに `claude -p` を動かさない。
