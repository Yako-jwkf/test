# 属性網羅型AI推論システムの設計の評価(2026-10-11)

要約: 利用者が貼った「属性網羅型AI推論システムの設計」の評価の到達点。骨組み(証拠DB・事実/推論/未解決の区別・目標の履歴)は良い。残る穴は「監査の独立の中身」「止まる条件」「確認済みの基準」の3つで、それぞれの案(A1〜A4、私の意見)をここに置く。目的は前もって決めない(利用者の言葉)。試し(A5)は独立監査1巡まで通した(2026-10-11)。独立監査が出した代わりの説明で、私の草案(ask の段が人の承認なしに通った)を撤回した。

## 設計の骨組み(原文は [mistake-cases.md の事例13](mistake-cases.md#事例13))
- 1 クエリを属性に分解 → 2 第1段の情報収集(新しい属性も回収) → 3 集めた情報を踏まえて AI が目標を決める → 4 目標を属性に分解(達成に要る情報と、目標の妥当性を確かめる情報を分ける) → 5 第2段の情報収集 → 6 3系統の検索(指定属性・関連属性・独立監査)と、自己評価だけに頼らない網羅性の点検 → 7 推論と再評価(目標が不適切なら 3 からやり直す。未探索が残れば追加検索) → 8 結論と根拠の対応・事実/推論/未解決の区別 → 9 データ構造(属性台帳・証拠DB・検索履歴・監査記録・目標履歴)。
- 設計原則(原文): 「AIが想定した属性を検索するだけでなく、独立した探索によって想定外の属性を発見し、その情報を目標設定と推論に反映できる構造にする。」

## 評価の基準
- 設計原則が実現できるか。物差しは設計が自分で書いた原則で、外の構成(この作業場のリサーチ Agent など)の決まりは使わない(2026-10-11 の撤回から)。
- 部品は、それが開く分岐(その先にできること)まで見る(2026-10-02 に利用者が決めた基準。[focus-tracking-design.md](focus-tracking-design.md))。

## 良い点
- 3: 目標を第1段の情報の後で決め、変えた理由を目標の履歴に残す。7 で「新たな情報によって」作り直す。私の読み: 「目的は成果物から生まれる」をそのまま手順にした芯の部分。
- 4: 「目標の達成に要る情報」と「目標自体の妥当性を確かめる情報」を分ける。
- 9: 証拠DBに取得日時と「根拠となる箇所」を持つ。

## 残る穴と案(案はどれも私の意見。未測定)

### A1 監査の「独立」の中身(6)
- 穴: 機械的な点検(未解決の依存関係・出典の追跡可能性)は台帳の中のつじつましか見ず、台帳に一度も載らなかった属性は「未解決」として出てこない。台帳の外を見るのは必須属性チェックリストだけで、誰が作るかが書かれていない。同じ AI が同じ文脈で作れば、見落とす場所も同じになると推測する。
- 案:
  - 独立監査検索は別の役が行う。渡すのは元のクエリと 7 の結論の草案(反証を探す相手)だけ。属性台帳・検索履歴・証拠DBは渡さない(同じ検索語に引っぱられないため)。
  - 必須属性チェックリストは、質問が来る前に分野ごとのひな形として作る。実行中に AI が足す項目は別の欄に書き、ひな形と混ぜない。
  - できれば別のモデルか別の検索源を使う。
  - 監査役が見つけた属性は、そのまま採らずに本体の台帳へ「見つけた系統 = 独立監査」で入れ、本体が証拠で確かめる。文脈を切ると判断の手がかりも減るため(下の根拠の 2026-10-03 の試験)。

### A2 止まる条件(2・5・7)
- 穴: 見つけた属性をさらに探し、7 は「未探索が残れば追加検索」。探すほど新しい属性が見つかると仮定すると、この条件では終わらない。目的を前もって決めないので、「目的を満たしたら止める」も使えない。
- 案: 飽和で止める。独立監査の1巡で見つけた新しい属性のうち、結論を変えたものが0件の巡が2回続いたら止める(2回は仮の値)。安全のために、検索の回数・費用の上限も持つ。上限で止めたときは、最終出力に「上限で止めた・未探索の属性あり」と書く。
- 外した候補: 予算だけで止める(結論を変える属性が残っていても止まる)。3 で決めた目標の評価基準で止める(7 で目標を作り直すたびに基準が動く)。

### A3 「確認済み」の段階(8)
- 穴: 8 は「確認済みの事実・推論・未解決」を分けるが、確認済みの基準がない。検索で見つけたものは「そう書いてある資料」で、基準がないと「検索で見つけた = 確認済み」になりやすいと推測する。
- 案: 証拠DBに2列を足す。
  - 確かさ: ①出典に書いてある ②独立した2つ以上の出典が一致する(同じ元の資料を引いた記事どうしは1つと数える) ③自分で計算・実行して確かめた。8 の「確認済みの事実」は ② か ③ だけ。
  - 読んだ範囲: 本文/要旨/要約。

### A4 属性台帳の列(9。いちばん先がある部品)
- 案: 属性台帳に「見つけた系統」(指定属性検索/関連属性探索/独立監査検索)と「結論を変えたか」(はい/いいえ/未判定)の2列を足す。
- 開く分岐: 独立監査だけが見つけた属性の数と、そのうち結論を変えた数を数えられる。設計原則が効いているかを、設計自身の記録で試せる。A2 の飽和の判定もこの列で行う。

### 細かい点
- 「再現可能」は、検索をやり直して同じ結果が出る意味では成り立ちにくい(Web は変わる)。保存した証拠から同じ結論をたどれる意味なら、証拠DBで足りる。

## A5 試し(2026-10-11、独立監査1巡まで)
- 質問(私が選んだ): 「Claude Code のクラウドのセッションを auto モードで使うとき、settings.json の ask に当たる操作は、人が承認するのか、自動で決まるのか」。開発の診断([dev-productivity-diagnosis.md](dev-productivity-diagnosis.md))で「承認の許可を押したのが人か自動か … 決め手がない」と残っていた点。
- 上限: 1問・1回・8ドル・検索と取得40回。使ったのは、私の検索・取得5回、会話の記録の読み取り、独立監査の役(サブエージェント)1回(取得12回)。独立監査は利用者の「ok」で使った。

### 結論(独立監査の後)
- 公式の説明(permission-modes のページ、本文。確かさ①): auto モードでも「Explicit ask rules still force a prompt.」。
- この会話の ask の段の操作12件(編集10件・git push 2件)のうち11件は、利用者の画面から許可の答え(サーバーの記録 `list_events` の `control_response` の `behavior: allow`)が返っていたことを確かめた(確かさ③)。残る1件(2回目の push、14:00)は jsonl の `user_temporary` だけで、サーバーの記録は見ていない。
- 会話の記録(jsonl)の `permissionDecision` は、10件が `source: user_temporary`、2件が `source: config`・`reasonType: mode` だった。2件(推論の手順の編集・最初の push)は、許可の答えが作業者の再起動の直前(13:37:25 と 13:58:58)に返り、再起動の後の新しいプロセスが `config`・`mode` と記録した。push の答えには、会話の間だけ `git commit` を許す規則の追加も入っていた(利用者が選んだ)。
- まとめ: 人が承認したかは、jsonl の `source` では決められない。サーバーの記録の `control_response` で確かめる。auto モードでも ask の段は人に聞いていた(この会話で確かめた11件)。

### 撤回した草案(独立監査の前)
- 「2件は人の答えなしに許可された。ask の段は再起動をまたぐと人の承認なしに通ることがある」。jsonl の印だけで決め、サーバーの記録(control_response)を見ていなかった。独立監査が出した代わりの説明(「人は答えていた。再起動で答えが新しいプロセスに届き、config と記録された」、根拠の強さ: 中)を、サーバーの記録で確かめて撤回した。ミス置き場の 2026-10-11 の行(C07)。
