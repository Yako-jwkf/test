# Control Plane v3(このリポジトリでの作り直し)

要約: v2.3(外部の ZIP)の考え方「AI は提案だけ、評価役は書き換えさせない、測ってから変える」を、自作の Python 門番ではなく Claude Code の permissions・フックと Git/CI で守らせる。段階0(境界)は実装し、このセッションで止まることを確かめた。

決定日: 2026-10-02(このリポジトリで作ると利用者が決定)

## なぜ作り直すか
- v2.3 の門番は動かして確かめると壊れていた。性能が落ちてもリリース判定が通る、成功率が常に0、保護対象の照合をすり抜けられる、ロールバックが未実装、承認が任意の文字列で通る。
- 原因は「守らせる仕組み」を自作したこと。Claude Code の permissions は deny → ask → allow の順に判定され、ask はどのモードでも自動許可されないので、承認はこちらに任せる。

## 方針
1. 守らせることは Claude Code と Git の仕組みに任せる。
2. 自作するのは「測る」部分(`/retest` とその拡張)と、境界の試験だけ。
3. 小さく始め、測ってから足す。

## 限界
- guard.py は文字列で判断する。試験の手順をファイルに書いてから実行したら、保護パスに触れる操作でも止まらなかった(コピー上の試験で実際に起きた)。`cd` してから相対パスで書く、変数でパスを組み立てる、なども同じ。
- 確実に止めるには sandbox が要る(deny ルールが sandbox の書き込み禁止にも入る)。しかしこのクラウド環境には `bwrap` がなく、仕様では依存が欠けると sandbox なしで動く。そのため sandbox は入れていない。ローカルで使う場合は `sandbox.enabled`・`allowUnsandboxedCommands: false`・`failIfUnavailable: true` を検討する。
- `retest-log.md` を Claude が書く以上、作り話の記録は防げない。CI では Claude を動かせないので、再実行による検出もまだない。
- ask の段は、Edit などファイル編集の道具を通したときだけ承認画面が出る。Bash の `git merge` や python で書くと、承認画面なしで変わる(2026-10-06、PR #7〜#9 の取り込みで実際にそうなった)。guard.py が見るのは deny の段だけ。ask のファイルの変更は、PR の審査で見る([改良案 E2](improvement-proposals-2026-10-06.md))。
- CI が赤でもマージを止めるには、GitHub 側でブランチの保護設定が要る。このリポジトリで使えるかは未確認。

## 保護ファイルを変える手順
段2のファイルは、編集のたびに承認画面が出るので、この手順は要らない。段1のファイルを変えるときだけ使う。
1. 利用者が「judge.md をこう変えたい」と依頼する。
2. Claude が `settings.json` から該当する deny を1行外す(ask の承認画面が出る)。
3. 対象を変更する。`check_boundary.py` はこの時点で NG になる。
4. deny を戻す(承認画面)。`check_boundary.py` が OK に戻ることを確かめる。
5. 1つの Pull Request にまとめ、利用者が差分を見てマージする。

**A. 学びを届ける(継ぎ目1)**

  - (b) SessionStart フックで、main に入っていない `claude/*` ブランチと、その中のミス置き場の行数を知らせる。

**B. 再発を測る(継ぎ目1・6・7)**
