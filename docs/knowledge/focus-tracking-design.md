## 分岐の基準での評価(2026-10-02)
| 部品 | 開く分岐 | 分かれ目(決めること) |
|---|---|---|
| 表示＝演出(演出のカウンタ) | 推定した状態で進みを遅く・止める(通知なしで伝える)/時刻に見えない数で時計を気にさせない/確定の瞬間を振り返りのきっかけにする/計算に触れずに表示の形を差し替える/表示の有無で集中が変わるかを測る | Focus Tracking には STOP がないので、演出の数字をどの時点で本当の値に確定させるか(箱の切り替え・離脱の推定など)。数を時間と読み違える・確定時に数が飛ぶ、も設計の対象 |
| Focus Box(箱を選んだら開始) | 箱の選択=利用者の宣言なので、自動推定の答え合わせに使える/箱ごとに推定を変える(読書の箱では無操作を離脱とみなさない)/切り替えの回数をそのまま数える/位置が固定なのでキー1つで開始 | 後からセッションを別の箱へ移せるか(移せれば「分類は後付け」と両立)。箱を選んでいない時間も観測するか |
| 後付けのラベル・「わからん」 | 付け直し/付けるまでの時間がデータになる/「わからん」の割合の推移/自由記入から新しい分類 | 「わからん」(本人が分からないと付けた)と「未分類」(まだ付けていない)を分けるか。分ければ「未分類をあとでまとめて振り返る」分岐が残る |
| セッションは観測の結果 | 離脱とみなすしきい値を変えて作り直す/推定の方法を改良しても過去を作り直せる | どの生の信号(1分ごとの操作回数、アプリの切り替えなど)を残すか。中身(打った文字など)を残さない線引き。残すほど保存量と負荷が増える(推測) |
| 連続的な状態(集中→低活動→離脱候補→明確な離脱) | 状態を表示に返す(演出のカウンタの速さ)/離脱候補から戻った時間を「考えていた時間」として数える | 何分以内に戻れば同じセッションか。離脱候補の時間を集中と離脱のどちらに数えるか(両方出す手もある) |
| 本人のリズムの集計(セッションを個別に残す) | 時間帯・曜日の比較/作業の並び(調べる→作る)/同じ箱に戻るまでの間隔/後から新しい指標 | 集計を利用者に返すか。返すなら観測器にとどまるか、助言までするか。返すと行動が変わり、観測も変わる(推測) |
| 予約(絶対的な終了時刻) | 「この箱に何時に戻る」の予定 | 時刻で戻らせるとポモドーロ的な押し付けに近づく。原則との兼ね合い |

- 私の意見: いちばん噛み合う組み合わせは「状態の推定 → 演出のカウンタの速さ → 利用者が通知なしで気づく」。行動を邪魔せずに記録を返せる道で、実時間のカウンタでは作れない。演出のカウンタを残す最も強い理由。
- 次に決めたい(私の意見): ①何分以内に戻れば同じセッションか ②演出の数字をどの時点で確定させるか。利用者の返事はまだ。

## 最初の評価(2026-10-02)から残っている点
- 経過時間は、時刻合わせで巻き戻らない時計(単調時計。例: JavaScript の `performance.now()`)で測るのが一般的。スリープ中に進むかは環境で違う(記憶。未確認)。
- 予約は残り時間を計算するだけでは鳴らない。アプリが止まっていても知らせるには、OS の通知予約などが要る。
- 平均集中41分などは実測ではなく推定値。しきい値で数字が変わるので、画面で「推定」と示す。
- Web アプリだと他のアプリでの操作は基本見えない(推測。未確認)。観測の範囲は作る環境で決まる。
- 計測: このコンテナの Node 22 で、時刻の読み取り1回 約70〜100ナノ秒、カウンタの足し算 約20〜30ナノ秒。毎秒60回描いても時刻読みは1秒あたり約6マイクロ秒。普通のアプリなら演出のカウンタの性能上の得は小さい。時刻を読むのが高くつく環境(AI が道具で時刻を取るなど)なら話が変わる。

## 撤回した主張
- 「演出のカウンタは要らない。手間は同じ」(2026-10-02 の最初の評価)。演出の目的(軽さ・進行感)を確かめずに欠点扱いし、手間も測っていなかった。分岐の基準で見ると、演出のカウンタは実時間のカウンタにない分岐を開く。
