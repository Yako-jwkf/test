要約: 指摘されたミスだけでなく、生の会話と開発履歴から知識を見つけ、未使用の事例で確かめ、使い回す仕組みの設計(案)と、最初の試験の記録。試験は、会話4件から候補10個を掘るところまで進めた。確かめる事例(事例8・13)にはどの候補も当てはまらない(私の読み)と分かったので、確かめる段階の前で止めた(未実施)。いちばん細いのは、知識を作る側ではなく、確かめる事例の側だった。

## 設計の要点(案。利用者は試験を進めることだけを了承。部品はまだ作っていない)
- 依頼: 利用者が 2026-10-11 に貼った「生クエリと開発履歴から知識を獲得する継続学習機構を設計する」(必須要件12、最初は設計と現状調査だけ)。
- 流れ: ①集める → ②掘る → ③台帳に置く → ④確かめる → ⑤採る・保留・撤回(人が決める)→ ⑥使う → ①に戻る。
- 既存の仕組みで済む部分: 対策の欄(作用の仮説・効果の基準と結果・副作用・決定・証拠。[mistake-causes.md](mistake-causes.md))、既知・未知・通常の区別([effect-evaluation.md](effect-evaluation.md))、決定の7語と14日の見直し候補(`scripts/mistake_check.py`)、deny・ask・追記のみの3段([control-plane-v3.md](control-plane-v3.md))、版を比べる `run.py`(`RETEST_PREV_REF` で比べる版を変えられ、mech は追跡していない新しいファイルも写す)。
- 新しく要る部分: 指摘のない成功を拾う決まり(いまの `/reflect` の入口は失敗だけ)、候補の欄の「種別(利用者の好み/一般/仮説)」「反例」「確信度」、日付で分ける決まりとその点検、機密の扱い。
- `/learn` は利用者が概念を学ぶ流れで、AI の知識獲得とは別物なので使わない。
- 成功の印: 「進めて」「ok」だけでは数えない。始める前に書いた完了条件を満たしたこと、後の会話で同じ箇所が直されていないこと、PR が戻されていないことを使う(2026-10-06 の C23 の発言は、先へ進める言葉だが不満の表れだった)。
- 確かめ方: 候補の根拠の会話の日付 < 台帳に入れた日 < 確かめる事例の日付。根拠と事例の会話が重なったら数えない。
- 機密: Yako-jwkf/test は公開(public)。原文はリポジトリに置かない。置くのは候補の文・会話の番号・日付だけ。原文の写しは scratchpad と /tmp にだけ置き、試験の後に消す。確かめる事例の原文は、利用者が1件ずつ同意したものだけを test に置く(2026-10-11、利用者が案 (a) を選んだ)。
- 集める対象: 利用者が許可した会話だけ。test が付いた会話にも、私生活の話や、ほかのリポジトリの話が混ざっている。

## 分かったこと
1. **取り出しが一番重い。** 4件で MCP の読み出しが136回かかった。1ページ100件のうち、返答は0〜4件しか入らない。前もって決めた上限(掘る役1回・答える役32ターン・judge 48体)には、取り出しの量を入れていなかった(ミス置き場の 2026-10-11 の行、C12)。
2. **サーバーの記録の「最後の返答」(result)は、利用者が読んだ本文とは限らない。** 停止フックが動いたターンでは、フックへの短い返事に置き換わる(会話C は12ターン中9)。本文は assistant の記録の text から取る。古い側の17ターンは、上限で本文まで取れなかった(印を付けて渡した)。
3. **候補の話題は、材料の会話の話題に寄る。** 4件が定期実行・news・スキルの話だったので、候補の多くもその場面のものになった。確かめる事例(事例8: 短い感想、事例13: 貼られた設計の評価)には、10個のどれも当てはまらない(私の読み)。10-09 以後に利用者が訂正した7行も、評価・語の範囲・判断の返しすぎ・数字の読みの場面だった。K04 に近い1行(10-10、C23)は、直前の返答がないと再現できない。
4. **自動モードの判定が止めた。** `claude -p --permission-mode bypassPermissions` を動かす流れのあとで、読むだけの操作が「Create Unsafe Agents」で止められた。ほかの会話から取り出した中身を状態ファイルに書く操作も、「Sensitive-Source Provenance」で止められた。`run.py` は答える役をこの設定で動かすので、自動モードのままでは流せない恐れがある(未確認)。
