# 効果の評価(対策が実際のミスを減らしたかの測り方)

要約: 対策の評価を「記録・動作・再生・既知・未知・通常・本番」に分け、効果と呼べるものを決める。基準は測る前に決め、変更前の結果を残してから、介入を1つずつ比べる。2026-10-09 に作った。変更前の基準値はまだ測っていない(費用の了承待ち)。

用語: 介入=対策を1つ足す・直す・外すこと。judge=再テストで答えを採点する AI(`/retest` 専用、変更に手順が要る)。

## 7つの評価の区別
対策が「ある」「動く」ことと、「ミスが減った」ことは別。効果と呼ぶのは、既知・未知・通常の3種類がそろって基準に届き、本番で再発がないときだけ。それでも「評価の範囲で」の意味。

| 評価 | 何を見るか | 道具 | 効果に数えるか |
|---|---|---|---|
| 記録 | 対策の文がファイルにある | `scripts/mistake_check.py` の `残存:` | 数えない |
| 動作 | フックが設計どおりに止める・通す。落ちない | `mistake_check.py` の `振る舞い:`(動作確認) | 数えない |
| 再生 | 置き場に記録した失敗の文を、フックが止めるか | `mistake_check.py` の `振る舞い:`(再生) | 数えない(フック単体の届く範囲) |
| 既知 | 対策を作るのに使った失敗の入力で、同じ失敗が起きないか(回帰の試験) | `run.py` + judge | 3種類の1つ |
| 未知 | 対策を作るのに使っていない失敗の入力で、起きないか(汎化の試験) | `run.py` + judge | 3種類の1つ |
| 通常 | ふつうの依頼の正答と、費用・長さ・道具の回数・検索の回数が悪くならないか(副作用の試験) | `run.py` + `scripts/eval_metrics.py` | 3種類の1つ |
| 本番 | 導入日より後に、同じ原因の行が置き場に増えたか | `mistake_check.py` の再発 | 最後の物差し。ただし分母(会話の量)がなく、指摘されたものしか載らない |

対策ごとの状態(未評価・評価中・効果確認済み・効果不十分・副作用あり・撤回済み)と、その決め方は [mistake-causes.md](mistake-causes.md) の「対策の状態の決め方」。

## 事例の集め方
- **既知**: `mistake-cases.md` の事例のうち、その対策を作るきっかけになったもの。
- **未知**: 本番で起きた新しい失敗で、原文があり、そのとき入っていた対策を作るのに使っていないもの。本番の失敗が起きたら、原文を事例にして、次の未知の試験にする。私が言い換えを作ることはしない(対策を知っている私が作ると、対策に合わせた易しい入力になりやすい。私の意見)。2026-10-09 時点で事例8(C02 の 2026-10-09 の行)の1件。
- **通常**: 作った依頼のうち、答えが1つに決まり、機械で判定できるもの。事例9〜12 の4件(リポジトリの中を探す・コードを読む・一般の質問・会話の区切り)。
- 試験の入力と条件は `mistake-cases.md` にだけ書く。このファイルと原因の表は、`run.py` が答える役のフォルダに写すので、事例の中身を書かない。

## 決め方(測る前に決めた。2026-10-09)
- 回数: 1ターンの事例は各条件5回。多ターンの事例は各3回(費用のため。差の読みは弱くなる)。
- 採点: 既知・未知は judge 2体、割れた条件だけ3体目で多数決(`/retest` 手順4)。通常は `eval_metrics.py` の機械判定。機械判定が不合格とした回は、答えを開いて確かめる。
- 比べ方(`eval_metrics.py` の定数と同じ。変えるときは両方を直す):
  - 合格の回数の差が2以上(5回以上のとき)なら改善・悪化。それ未満は「差なし(誤差の範囲)」。5回未満なら判定保留。
  - 費用・長さ・道具の回数の中央値が1.3倍を超えたら「悪化の疑い」。検索の回数が0から増えたら「悪化の疑い」。
  - 疑いは、もう一度5回流して同じなら、原因の表の副作用に「確認:」として書く。1回だけなら「疑い:」。
- 条件をそろえる: モデル(`run.py` の既定)、入力(原文のまま)、採点(上の手順)、版を書き残す。
- 1つずつ: 変更前は `RETEST_PREV_REF=<変更の直前のコミット>` の `prev`、変更後は作業中の版の `mech`。差が1つの介入だけになるようにする。2つの介入が同じ失敗に効くと疑われるときは、両方入れた版も流す。
- 本番でもよくなったとは、試験の合格だけでは言わない。「効果確認済み(評価の範囲)」の後も、本番の再発を見続ける。

## 流し方
1. 出力フォルダ(scratchpad の下)に `plan.md` を書く(`測りたいもの:` `使う条件:` `費用の見込み:` `結果で決めること:`)。費用の見込みを利用者に見せて了承を得る。
2. `python3 .claude/skills/retest/run.py <事例> <回数> <出力フォルダ> <条件>` を、Bash の run_in_background で動かす。
3. 通常タスク: `python3 scripts/eval_metrics.py summary <出力フォルダ> <事例>`。変更前と後: `python3 scripts/eval_metrics.py compare <前> <後> <事例> <条件>`。
4. 既知・未知: `/retest` 手順4で judge に採点させる。
5. 結果を [retest-log.md](retest-log.md) に足し、原因の表の対策の「効果の結果」「副作用」に日付つきで書いて、`python3 scripts/mistake_check.py --write` を動かす。

費用の目安: 1ターンの事例は1回 0.15〜0.45 ドル(2026-10-08 の `/stress` の実測、33回)。事例2(5ターン)は3回で約13〜15ドル(retest-log)。

## 原因の分析(2026-10-09、C01・C02・C07・C08・C09)
置き場の行と対策を照合した結果。「直接の原因」は行を読んだ私の読み。

| 原因 | 直接の原因 | 今の対策が作用する範囲 | 再発の説明 | 分け方 |

| C08 | 結論に条件を書かない | M09 は7つの語だけを見る | 再生で、記録した失敗の文6つのうち止めるのは、作るきっかけの2つだけ | C07・C09 と重なる |
| C09 | 候補を直前の話題という狭い枠からだけ作った | M10 は書く形(目的・外した候補)を求める | 10-02 は外した候補を同じ枠から挙げ、形は満たしていた | 候補の作り方の問題 |

まとめ(私の意見): 今の対策は出力の**形**を求めるか見張るもので、失敗は中身を作る段(読み取り・候補の出し方・根拠と主張の結びつけ)で起きている。だから形を満たしたまま再発する。ルール・手順・フック以外に要りそうな手は、次の4つ。
- 本番の失敗を未知の試験にして、介入を測る
- 2通りに読める依頼は、実行の前に利用者に確かめる
- 効かない対策を撤回して、指示の量を減らす
- 機械で確かめられる部分(自分の編集の後に試験を流す、引用が原文にあるか)は道具で確かめる

どれも、入れる前に上の決め方で測る。
