# 文章推敲スキル(/proofread)のテスト記録

要約: `/proofread` の本文は、ユーザー案に出力形式と「直すか確認に回すか」の判断を足した混合版。4事例×3回の再テストで、スキルなしより明確に良く、慎重さを上げた改訂版は「直せる箇所を直さない」退化を起こしたので不採用にした。

## 方法(2026-10-01)
- 推敲役: `subject-bare`(CLAUDE.md を読まないサブエージェント)。スキル本文を依頼文に貼って渡した(`/proofread` として呼んだ場合と同じ動きかは未確認)。
- 採点: `judge`(別モデル)が「良い答えの条件」ごとに合格/不合格。各条件3回。
- 条件: スキルなし / 案そのまま(ユーザーの14項目案) / 改訂版(例文修正+「対象が変わっていたら取り消す」規則) / 混合版(採用)。

## わかったこと
- スキルなしだと、原文にない手順を足す(A5)、参照先のない「これ」を推測で埋める(B3)、問題のない文を書き換える(C1)、無関係な文まで直す(D3)が毎回起きた。
- 「対象が原文と変わっていたら変更を取り消す」という規則を足すと、文脈から解決できる指示語まで直さなくなった(改訂版 D1・D2 が 0/3)。慎重さを上げる規則は効きすぎる。
- 例文がルールと矛盾していても(「落ちることがあります」など)、直後の「ただし〜しない」が守られ、実害は出なかった。混合版では矛盾は解消した。
- 最初の事例Aは「サービスAとBを再起動…それが正常に起動した」で、文脈から「両方」と読めてしまい、「勝手に決めない」という条件の方が誤りだった。事例は「本当に決められない」文にする必要がある。

## 事例(再テスト用。入力は原文のまま)

### 事例A(解決できない「それ」+ 変えてはいけない文)
入力:
```
キャッシュサーバーの設定を変更し、DBサーバーの接続数を増やしてください。その後、それを再起動します。この処理はメモリを食うので、大量のデータを一気に渡すと落ちます。APIが401を返した場合はトークンの期限切れです。
```
条件:
1. 「それ」の参照先をキャッシュサーバー・DBサーバー・両方のどれか一つに本文で決めて書き換えていない(本文は原文のままにして、不明である旨を指摘・確認している)。
2. 「落ちます」を「落ちることがあります」「可能性があります」などの不確実な表現に変えていない。
3. 「メモリを食う」を残すか言い換えるかに関わらず、OOM・プロセス終了・メモリ上限などの原文にない仕様を追加していない。
4. 「APIが401を返した場合はトークンの期限切れです」の主語を人間や別の語に変えず、「期限切れです」の確実さを変えていない。
5. 原文にない情報(数値、具体的なコマンド、手順、製品名)を追加していない。

### 事例B(抽象度を保つ)
入力:
```
データを保存する前に確認してください。確認が終わったら、キャッシュを有効にします。キャッシュを入れるとパフォーマンスが改善します。設定を変更すると、これを防ぐことができます。
```
条件:
1. 「データを保存する前に確認してください」に、原文にない確認内容(スキーマ、必須項目、形式、DB など)を足していない。
2. 「パフォーマンスが改善します」を、原文にない具体的な指標(レスポンス時間、DBアクセス回数、スループットなど)に置き換えていない。
3. 「これを防ぐ」の「これ」が何を指すかを勝手に具体化して本文に書いておらず、不明である旨を指摘または確認している。
4. どこを変えてどこを変えていないかが分かる(変更一覧、または変更箇所の説明がある)。

### 事例C(問題なし。変えてはいけない)
入力:
```
Redisはインメモリデータストアです。キャッシュとして使用できます。キャッシュを使うとDBへのアクセスを減らせます。管理者としてログインした場合のみ、APIを利用できます。
```
条件:
1. 4つの文のいずれも語順・語彙を変えていない(修正後の本文が原文と同一である)、または「変更なし」「修正不要」と明示している。
2. 「Redisは」「キャッシュを使うと」などの非生物主語を人間主語に書き換えていない。
3. 原文にない情報(Redis の仕様、数値、用途の説明など)を追加していない。
4. 「管理者としてログインした場合のみ」の条件を落としたり緩めたりしていない。

### 事例D(原文から解決できる「それ」。直すべき)
入力:
```
設定ファイル config.yml と secrets.yml を作成します。config.yml には接続先を書きます。secrets.yml には認証情報を書きます。作成したら、それを読み取り専用にしてください。パスワードが含まれているためです。
```
条件:
1. 「それ」を secrets.yml と特定して本文を直している(「secrets.yml を読み取り専用に」のように書いている)。
2. 「それ」が secrets.yml である根拠として、パスワード(認証情報)が含まれることに触れている。
3. 「config.yml には接続先を書きます」「secrets.yml には認証情報を書きます」を書き換えていない。
4. 原文にない情報(chmod などのコマンド、権限の数値、手順、理由の追加)を追加していない。

## 限界
- 各条件3回で、採点係も AI。事例は短い作り物で、長文での挙動は未確認。
- 事例A・Bの文はスキルの例文と同じ文を含む(例文をまねるかを試すため)。C・D は例文にない文。

## 根拠
- セッション「文章推敲スキルの評価とテスト」(2026-10-01)。答えと採点の全文はセッションの scratchpad(`proofread-test/`)にあり、リポジトリには残していない。
- スキル本文: `.claude/skills/proofread/SKILL.md`

## 追試(2026-10-01、採用版で13本の難しい文章)

ユーザーが用意した13本(参照の競合、条件のスコープ、主体の切り替わり、因果の補完、抽象語、時系列、否定と例外、AI文体、複数の指示語、専門家向け、冪等性、罠盛り)を、見出しを外して1回ずつ流した。

- 本文を壊した例はなし。9本は変更なし、4本は1語〜1句の補い(「ファイルが」「決済が」「並列数を」「再試行します」)。補った語はすべて原文にある語。
- 本当に決められない箇所(競合する「それ」、3通りに読める「これ」、順序の矛盾)は本文を変えず「確認したい点」に回した。
- 「否定と例外」の文(「…認証エラーについては行いません。ただし、認証サーバー自体がタイムアウトした場合はこの限りではありません。」)は、「この」がどちらの規則の例外かで結果が逆になる。4回流して、1回は一方の読み(再試行する)に決めて本文を書き換え、3回は変更せず両方の読みを質問した。決められない箇所を一方に決めた例はこの1回のみ。
- 「確認したい点」は1本あたり3〜8件。原文が意図的に省いている主体(「誰が再試行するか」など)を毎回尋ねる傾向がある。本文には影響しない。

## 「一方に決めない」規則の追加を試して、見送った(2026-10-01)

弱点「読み方で結果が逆になる箇所を、たまに一方に決める」に対して、規則を1行足す案を2つ試した。どちらも事例D(直すのが正解)で退化したので、スキル本文は変えていない。

| 版 | モデル | 事例G(直さないのが正解) | 事例D(直すのが正解) | 事例C |
|---|---|---|---|---|
| 採用版 | Fable 5.1 | 3/4 | 3/3 | 「決済が」を補う 1/1 |
| 案1「動作や対象が変わる箇所は一方に決めない。根拠は名指しの語だけ」 | Fable 5.1 | 5/5 | 0/3 | 「作成した注文」のみ。「決済が」は補わず 3/3 |
| 採用版 | Opus 5.5 | 5/5 | 3/3 | 「決済が」を補う 2/2 |
| 案2「動作が逆になる箇所は一方に決めない」 | Opus 5.5 | 5/5 | 0/3 | 「作成した注文」「決済が」 2/2 |

- 案2は範囲を「動作が逆になる」に絞ったが、推敲役は D の「それ」も「config.yml を読み取り専用にするかどうかが逆になる」と読み替え、直さなかった。参照先の曖昧さはほぼ必ず「動作が変わる」と言い換えられるので、この線引きでは D と G を分けられない。
- D と G の本当の違いは、D には理由の文(「パスワードが含まれているため」)と「認証情報」の対応という手がかりがあり、G にはないこと。ただし案1のように「名指しの語だけ」と厳しくすると、D の手がかりも推測扱いになる。
- 途中でモデルが Fable 5.1 から Opus 5.5 に変わった。採用版は Opus 5.5 では G を5回とも直さず、D は3回とも直した。Fable 5.1 で見えた G の取りこぼし(4回中1回)は、Opus 5.5 の5回では出なかった。
- 結論: 規則は足さない。G のような取りこぼしが実際の文書で再発したら、その実例をもとに改めて考える。

### 事例E(読み方で結果が逆になる例外。直さないのが正解)
入力:
```
すべてのリクエストを再試行するわけではありません。タイムアウトの場合は再試行しますが、認証エラーについては行いません。ただし、認証サーバー自体がタイムアウトした場合はこの限りではありません。
```
条件:
1. 「この限りではありません」を「再試行します」「再試行しません」など一方の動作に書き換えていない。
2. 「この」が「認証エラーは再試行しない」と「タイムアウトは再試行する」のどちらの例外かで結果が逆になることを、確認したい点に挙げている。
3. 原文にない情報(再試行の回数、HTTP ステータス、主体の名前)を本文に足していない。

### 事例F(確認したい点に原文にない具体例を書く癖の確認用)
入力: 事例D と同じ文。
条件:
1. 本文には原文にない情報を足していない。
2. 確認したい点の選択肢に、原文にない具体名(権限の値、コマンド、接続文字列などの形式)を書いていない。
