# ミスの原因の表

要約: ミス置き場(出来事)の行を原因ごとに束ね、原因ごとに「推測した原因・置いた対策・擬似解消関数」を持つ。対策は下の「対策の一覧」に1つずつ登録し、動作(動くか)と効果(実際のミスが減ったか)を分けて判定する。判定は `python3 scripts/mistake_check.py`。対策を置いたこと・対策が動くこと・既知の失敗例に合格すること・ミスが減ったことは、それぞれ別に扱う(2026-10-09)。

## 書き方(原因)
- 原因ごとに `### Cnn 名前` の節を1つ作る。置き場の行の「原因」の列に、この番号を書く。
- 各節は次の項目を、`- 項目: 内容` の形で書く。
  - 原因の推測: なぜ起きたか。種類(推測/確かめた)を先頭に書く。
  - 対策: 置いた対策と場所。まだなければ「なし」、見送ったら「見送り(理由)」。
  - 対策日: 対策を置いた日(YYYY-MM-DD)。この日より**後**の出来事を再発と数える。同じ日の出来事は数えない(日付しか持たないため)。
  - 擬似解消関数: 判定の方法。`、` で区切って複数書ける。
    - `振る舞い:名前` — 記録した入力でフックなどが期待どおり動くかを、台本(`scripts/mistake_check.py` の同じ名前の関数)で試す。
    - `再テスト:事例N-条件M>=k/n` — `/retest` の結果で判定する。結果は下の「最後の再テスト」に書く(台本は `/retest` を流さない。費用がかかるため)。
    - `残存:ファイル:文字列` — 対策の文がまだ残っているか。効き目ではない。
    - `なし(理由)` — 文字では判定できない。再発の数だけで見る。
  - 最後の再テスト: `事例N-条件M=k/n(YYYY-MM-DD)` を `、` で区切って書く。対策日より前の結果は「古い」として判定に使わない。
- 原因の分け方は私の読み(推測)。分け方を変えたら、置き場の「原因」の列も直す。

## 原因の状態の決め方(台本の判定)
上から順に当てはまったものにする。「動く」「対策の文がある」「既知の失敗例に合格した」は、どれも効果(実際のミスが減った)ではないので、名前で分ける(2026-10-09 まで、これらをまとめて「合格」と呼んでいた)。

| 状態 | 条件 |
|---|---|
| 見送り | 対策が「見送り」 |
| 未対策 | 対策日がない |
| 再発あり | 対策日より後に、同じ原因の出来事がある(本番の再発) |
| 動作不良 | 振る舞いか残存の確認が不合格(フックが落ちた・期待どおりに動かない・対策の文がない) |
| 既知の失敗例で不合格 | 対策日より後の再テストが基準に届かない |
| 既知の失敗例で合格(未知・通常タスクは未評価) | 対策日より後の再テストが基準に届いた。その対策を作った事例で測っただけなので、効果とは呼ばない |
| 動作のみ確認(効果は未評価) | 振る舞いの確認だけが通った |
| 記録のみ確認(効果は未評価) | 残存の確認だけが通った |
| 効果は未評価 | 判定できる関数がない(再発がないだけ) |

## 書き方(対策の一覧)
- 対策ごとに、下の「対策の一覧」に `### Mnn 名前` の節を1つ作る。1つの原因に対策が複数あれば、別々の節にする。撤回しても節は消さず、撤回日を書く。
- 各節は次の項目を、`- 項目: 内容` の形で書く。
  - 原因: 対象の原因の番号(`、` で区切る)。
  - 場所: ファイルと、その中のどこか。
  - 導入日: 今の形の対策が main に入った日。対策を直したら、この日を直す(前の結果は「今の形では未測定」になる)。この日より後の、対象の原因の出来事を本番の再発と数える。
  - 作用の仮説: どの失敗の起き方に、どう作用するはずか。作用しない範囲も書く。
  - 動作確認: 対策が設計どおりに動くか(`振る舞い:名前`・`残存:ファイル:文字列`)。効果には数えない。
  - 再生: 置き場に記録した失敗の文を、フックが止めるか(`振る舞い:名前`)。フック単体の届く範囲を見るだけで、効果には数えない。
  - 効果の基準: 結果を見る前に決める。`既知:事例N-M>=k/n`(過去の失敗の再発を見る回帰の試験)・`未知:…`(その対策を作るのに使っていない失敗。言い方や文脈が違うもの)・`通常:…`(ふつうの依頼で、正答や手間が悪くならないか)。事例がまだなければ `未知:なし(理由)`。測り方は [effect-evaluation.md](effect-evaluation.md)。
  - 効果の結果: `既知:事例N-M=k/n(YYYY-MM-DD)`。今の形より前の形で測った結果は、括弧の中に「前の形」と書く(今の形の効果に数えない)。
  - 副作用: `確認: …`(今の形で測って分かったもの)・`疑い: …`(前の形の結果や推測)。なければ「なし」。
  - 撤回日: 撤回した日。撤回の前に、必要性・副作用・代わりの手を確かめる。

## 対策の状態の決め方(台本の判定)
動作と効果は別の列に出す。状態は、下の順で最初に当てはまったもの。

| 状態 | 条件 |
|---|---|
| 撤回済み | 撤回日がある |
| 副作用あり | 副作用に「確認:」がある、または通常タスクの基準に届かない(今の形の結果) |
| 効果不十分 | 導入日より後に対象の原因の出来事がある(本番の再発)、または既知・未知の基準に届かない(今の形の結果) |
| 効果確認済み(評価の範囲) | 既知・未知・通常の3種類の基準がそろい、今の形の結果がすべて基準に届き、本番の再発がない |
| 評価中 | 今の形の結果が1つ以上あるが、3種類がそろっていない |
| 未評価 | 今の形の結果がない(動作確認が通っていても未評価) |

動作の列: 動く(動作確認がすべて通る)/動作不良(1つでも通らない)/確認なし。効果確認済みでも「評価の範囲で」の意味で、本番でミスがなくなったことまでは言えない。本番の再発は別の列に出す。

見直し候補(改良案 C1): 動作不良・副作用あり・効果不十分の対策と、導入から14日たっても未評価か評価中の対策、一覧に対策がない原因で再発あり・動作不良・既知の失敗例で不合格のもの。候補は「直す・撤回する・残す(理由)」を決める入口で、候補になっただけでは消さない。本番の再発は原因ごとに数えるので、働く場面が限られた対策(例: /reflect の中だけで働く M07)にも、その場面の外の再発が付く。見直しでは、再発の行がその対策の場面に当たるかを読んでから決める。
